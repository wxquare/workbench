## ADR-001 语言与服务框架

**背景**

工作流编排、Agent 工具循环、数据处理脚本与模型生态集中在 Python；同时需要对外提供 HTTP/SSE 接口、Schema 校验和生成的 OpenAPI。团队规模小，首版没有独立运维多个微服务的能力，也没有跨语言团队协作的需求。

**决策**

- 语言固定 Python 3.12。
- 服务用 FastAPI + Pydantic v2 实现，API、认证依赖、Schema、OpenAPI 与 SSE 共用一套定义。
- 采用"单体进程组"：`api` / `worker` / `scheduler` 三个进程共享同一份代码、配置和数据库，而不是拆成多个可独立部署的服务。
- 管理前端用 Vue 3 + TypeScript + Vite + Element Plus，构建产物由 API 从 `/app/` 同源托管。
- 依赖用 uv + uv.lock 完整锁定。

**代价**

- 进程组共享数据库意味着水平扩展受限于存储后端；SQLite 首版只能单机部署。
- Python 的异步与阻塞边界需要严格控制，否则长任务会占满事件循环。
- 前端同源托管牺牲了独立发布能力：前端变更要随 API 一起构建。
- uv.lock 全量锁定使框架升级（LangChain/LangGraph）成为一次需要回归恢复兼容性的动作。

**状态**

已采纳并落地。扩展路径见 [ADR-003](#adr-003-storagebackend-统一持久化契约) 与 [ADR-010](#adr-010-sqlite-先行)。

## ADR-002 外层业务图 + 内层专家图

**背景**

业务需要两类不同的控制：一类是固定顺序的业务流程（受理 → 取证 → 校验 → 出结论 → 归档），需要状态、检查点、人工中断与恢复；另一类是"在固定专家和工具集合内反复调用模型"的循环，需要工具调度与结构化输出。用一套机制同时表达两者，要么流程不可控，要么工具循环写死。

**决策**

- 外层用 LangGraph `StateGraph` 表达业务拓扑：节点、边、条件分支、检查点、`interrupt` 人工中断、`Command(resume=…)` 恢复。
- 内层用 LangChain `create_agent` 表达专家工具循环；专家被限制在固定模型角色和已发布工具集合内。
- 平台运行时（Worker、Execution、PolicyToolExecutor、ResultProjector）负责任务租约、取消与期限、当前授权、工具台账、证据与最终业务状态——这些不交给图或 Agent。

**代价**

- 两层编排意味着两次状态：图状态（业务）与 Agent 内部消息（专家），二者的边界必须显式定义，否则错误会被吞在里层。
- `interrupt` 恢复会重新执行节点入口代码，节点必须可重入。
- 框架版本升级同时影响两层，回归范围大于单一框架。
- 开发者需要理解两层各自的失败语义（图失败 vs 工具失败）。

**状态**

已采纳并落地。约束详见 [02 架构 §2.4](02-architecture.md#24-两层编排langgraph-与-langchain)。

## ADR-003 StorageBackend 统一持久化契约

**背景**

首版要快，SQLite 是最小依赖的选择；但业务明确预期未来换 MySQL/PostgreSQL。如果业务表用一种存储、检查点另放一种存储，就会出现"图状态已提交但业务状态未提交"的跨库不一致，而 LangGraph 自带的后端往往直接绑定具体数据库。

**决策**

- 定义 `StorageBackend` 端口，统一负责 `create_uow`、`capabilities`、`clock`、`health`、`migrate`。
- 业务表、Job、执行租约、检查点、事件、预算和 Outbox 全部使用同一后端与同一数据库事务。
- LangGraph 通过 `PortableCheckpointSaver` 调用同一 `CheckpointStore`，不自带数据库连接。
- 驱动与方言差异收敛在后端适配器；业务服务不依赖 SQL 方言特性（如 `SKIP LOCKED`）。

**代价**

- 抽象层增加了间接性：简单查询也要经过 Repository → UnitOfWork → Backend。
- 首版只有 SQLite 一个实现，抽象的正确性缺少第二个实现的检验，迁移成本可能被低估。
- 跨引擎迁移需要版本化逻辑导出（StorageTransfer），不能直接 dump；这是一块必须自建的工程。
- 事务边界必须由业务层显式管理，写事务内禁止模型/网络调用——这条约束靠评审而非编译器保证。

**状态**

已采纳并落地（SQLite 实现）。第二个后端适配器尚未实现，见 [02 架构 §16](02-architecture.md#16-已知缺口与评审问题)。

## ADR-004 用数据库表做持久化任务队列

**背景**

Run 受理后需要异步执行，且必须满足：受理即持久（返回 202 不丢任务）、Worker 崩溃可恢复、同一 Job 不被两个 Worker 同时执行、可按优先级和团队公平调度。引入 Redis/Kafka 作为消息队列会增加一个必须与数据库保持一致的状态源。

**决策**

- `run_jobs` 表就是持久化队列；`JobStore` 通过 `UnitOfWork` 和条件更新原子领取。
- API 在同一个数据库事务中写入 Run、输入消息、RunEvent 和 Job，提交成功后才返回 202。
- Redis 只承担"唤醒信号"：降低轮询延迟；未部署或信号丢失时 Worker 仍从 JobStore 轮询领取，可降级。
- P0 用 SQLite 短写事务；后续后端可在适配器内用行锁或 `SKIP LOCKED` 优化竞争，但业务服务不依赖这些 SQL。

**代价**

- 轮询带来延迟与空转；SQLite 下写竞争靠重试消化。
- 队列表与业务表争用同一把写锁，长事务会放大排队。
- 队列的可见性、死信、重放等能力要自己实现（当前体现为 Job generation、attempt 与 Outbox 状态）。
- 单机 SQLite 上限决定了首版 Worker 只能一个实例。

**状态**

已采纳并落地。

## ADR-005 四套状态机分离

**背景**

早期容易把"任务状态"当成一个字段：Run 跑完就代表一切完成。但实际上分析结果落库、外部动作执行、消息投递是三个独立失败面，任一失败都不应回滚或重开业务结论。

**决策**

- Run 状态、Job 状态（含 ExecutionLease）、Action 状态、Outbox 投递状态各自独立管理，不互相代替。
- `succeeded` 的含义是：分析结果已持久化、必要的业务记录已提交、待投递动作已入 Outbox；**不**表示外部系统已确认接收。
- `waiting_input` / `waiting_approval` 释放执行租约和 Worker 槽位，但保留 Thread 的活动 Run 位置。
- 外部动作发送后未确认结果进入 `unknown`，通过查询或人工对账收敛，不盲目重发。

**代价**

- 客户端需要理解三种状态来源：202 表示受理、SSE delta 是草稿、Run 终态不代表投递完成。
- 增加了状态组合的语义负担：Run 成功但投递 unknown 是合法状态。
- 对账路径（unknown → 已确认/失败）需要人工或额外查询能力，自动化程度受下游系统限制。
- 组合约束必须写成文档并测试，否则容易被简化为单一状态机。

**状态**

已采纳并落地。组合约束表见 [02 架构 §6.4](02-architecture.md#64-状态与所有权的组合约束)。

## ADR-006 受理固定版本 + 执行实时复核

**背景**

同一 Run 在排队、等待用户、Worker 接管之后可能跨越很长时间；期间 Agent 配置、模型、Skill、工具都可能发布新版本，也可能被停用或撤权。若执行时重新解析"最新配置"，同一 Run 在重启前后行为会改变；若完全信任受理时的快照，撤权后仍会继续调用已失权的资源。

**决策**

- 受理时把已发布的 Profile、图版本、模型、Skill、工具、仓库与 WorkflowVersion 固定进 `RunContext`，以 `VersionRef = {resource_id, version, content_hash}` 表达。
- Worker 在实际读取资源、调用模型或工具时重新检查当前团队、Agent 与部署权限。
- 两种变化区别处理：**发布新版本** → 旧 Run 继续用旧版本；**停用/撤权** → 下一次受保护操作复核并拒绝。
- 禁止通过"恢复时重新解析最新 Profile"掩盖旧版本资源缺失。

**代价**

- 每次资源读取都要额外做一次授权与哈希校验，路径更长。
- 旧版本对象必须长期保留，否则等待中的 Run 会因对象被清理而失败；清理策略要额外判断引用。
- 版本与权限两条语义容易混淆，文档和错误码必须区分"版本已固定"和"当前无权限"。
- 哈希校验失败的故障处理（`capability blocked` / partial）需要运维介入。

**状态**

已采纳并落地。语义表见 [02 架构 §3.8](02-architecture.md#38-受理快照与当前授权的时间差)。

## ADR-007 移除 Workspace 领域实体

**背景**

早期模型是 Team → Workspace → Thread → Run，Workspace 既被当作"项目空间"又被当作"配置容器"和"权限边界"。实践中它承担的三件事分别由团队（权限）、Agent（配置）和 Thread（会话）承担，Workspace 变成了必须同步维护的中间层，并且导致表名、字段和前端概念层层嵌套。

**决策**

- 领域直接是 **Team → Agent → Thread → Run → Job**，Workspace 从产品与领域层移除。
- 每个 Agent 有独立的 `agents.agent_id` 和自己的 RuntimeProfile；Thread、Run、资源绑定、权限范围与幂等回执直接归属 Agent。
- 数据库在 `schema_agent_v1` 中机械替换 `workspaces`→`agents`、`workspace_id`→`agent_id`；不在其上保留映射层。
- 旧 Workspace 迁移链 `schema_v1…v20` 保留为历史，不是 Agent 库的升级路径。

**代价**

- 已有 Workspace 数据库不能原地升级：`0001_agent_domain` 只在全新库上执行，旧部署需要重建与数据搬运。
- 一处命名变更波及面大：表、列、索引、配置、前端路由、文档、图示都要同步，遗漏会留下"幽灵 workspace"。
- 失去"一个 Workspace 聚合多个 Agent"的容器概念；如果未来确实需要分组，需要新增显式实体而非复用旧名。

**状态**

已采纳并落地（代码、迁移、文档图示已一致）。

## ADR-008 MCP Server 独立服务

**背景**

诊断取证能力（知识、指标、日志、Trace）面向的是一组外部数据源，身份、凭据、超时与配额与业务服务完全不同。若把它做成 Agent 进程内的模块，Agent 的 Run 权限会与下游数据源凭据纠缠，且无法被其他 MCP 客户端复用。

**决策**

- MCP Server 是独立 Python 包与独立进程（`workbench-mcp-server`），不与 Agent 共享代码或进程。
- 分层为 interfaces → application → domain，infrastructure 实现端口；业务层不反向依赖 bootstrap。
- 身份分两层：入站身份识别调用者与允许范围，出站身份访问下游；入站 token 禁止转发给下游。
- 授权按 `principal.tools`、`principal.scopes` 与 `source.scopes` 求交集，范围必须匹配完整元组 `(team, environment, region, service, source_id)`。
- 只提供四个只读工具，统一 `dod-tool-result-v1` 结果协议。

**代价**

- 多一个需要部署、配置、监控和升级的进程。
- 两层身份与授权交集带来配置复杂度，缺少维度即 `invalid_input`，调试成本高。
- 首版的 `normalized-http-v1` 是自定义网关协议，真实平台仍需专用适配器。
- 配置为启动时不可变快照，权限变更需受控重启，不支持对在途调用即时撤权。

**状态**

已采纳并落地（工具与协议）；真实数据源适配见 [02 架构 §12.5](02-architecture.md#125-当前边界)。

## ADR-009 直接问答与知识问答分图

**背景**

"这是什么""帮我解释一下"这类请求不需要检索、证据与 RCA 结构；如果走完整八节点链，会引入不必要的延迟、预算消耗，以及"为什么没有找到证据"的伪失败。反之，知识问答必须带引用，且其结果不能声称已验证。

**决策**

- `dod.v17`（单轮）与 `dod.v18`（多轮）是纯模型回答图：`START → answer → END`，不传 QueryScope 和工具列表。
- `dod.v16` 是带检索的知识问答图，`outcome` 恒为 `partial`——检索不等于验证。
- 直接问答的模型回复后追加固定提示"以下内容由模型生成，未经外部知识源验证。"
- `dod.v18` 的历史只取同 Agent 同 Thread 内已完成的 v17/v18 成功结果，最多 8 轮、正文上限 16000 字节。

**代价**

- 图数量增加，路由与版本管理更复杂。
- 用户可能在不适合的场景使用直接问答并误以为是"分析结论"；固定提示只能降低而不能消除误解。
- 历史裁剪依据轮数与字节上限，长对话可能丢失关键上下文。
- 两条路径的预算、可观测字段与测试用例都需要分别覆盖。

**状态**

已采纳并落地。

## ADR-010 SQLite 先行

**背景**

首版要能在单机、无 DBA、无外部依赖的前提下跑通完整链路：受理、执行、检查点、恢复、预算、投递。跨主机多实例、高并发写入不是当前阶段的问题。

**决策**

- P0 使用 SQLite 3.51.3+，启动时校验链接库版本。
- 部署约束：单机、单 `worker` 实例、2 个 Run 并发、短写事务。
- WAL 只用于本机持久磁盘，**不**放在跨主机共享文件系统上。
- 后续 MySQL 8.4 / PostgreSQL 16+ 通过同一 `StorageBackend` 契约接入，验收通过后才开放多主机部署。

**代价**

- 单写者模型限制了吞吐与并发；写竞争靠重试和短事务消化。
- 备份恢复是"文件 + 隔离"的运维动作，需要专门的 runbook，而不是数据库高可用方案。
- 不能共享存储做多实例，故障恢复窗口取决于单机。
- 抽象层未经第二后端检验，迁移风险后置。

**状态**

已采纳并落地。备份恢复见 [04 运维 §3](04-operations.md#3-sqlite-备份与恢复)。

## 如何新增一条决策

1. 分配下一个未被使用的 `ADR-编号`，在本文顶部表格追加一行。
2. 固定写四段：背景（问题与约束）、决策（做什么、不做什么）、代价（明确的负面后果）、状态（已采纳/试点/已取代）。
3. 如果新决策推翻旧决策，不要删除旧条目；在新条目"状态"里写"取代 ADR-xxx"，并回填旧条目为"已被 ADR-xxx 取代"。
4. 决策正文只写结论与约束；实现细节链接到 [02 架构](02-architecture.md) 与 [03 开发](03-development.md)，字段与配置链接到 [06 参考](06-reference/)。
