## 目标与边界

用户先克隆私有仓库，再在源码目录运行脚本。源码始终留在克隆位置，不提供远程一键安装或全局命令入口。本期借鉴 Hermes Agent 的默认目录加可覆盖目录方式，但保留 Workbench 显式建库的安全边界。

安装、首次数据库初始化和日常启动继续分别由 `scripts/install.sh`、`scripts/init-db.sh`、`scripts/start.sh` 负责。Docker Compose 使用现有命名卷，不纳入这次本机路径改造。

## 路径契约

- 默认持久数据目录为 `$HOME/.workbench`。`install.sh --data-dir /absolute/path` 可指定其他目录；不提供交互式提示，便于自动化。
- 安装脚本将选定的绝对路径写入 Git 忽略的 `config/local/data-dir` 纯文本文件。文件只保存路径，不保存密钥，也不作为 shell 代码执行。未指定 `--data-dir` 时，已有选择保持不变；没有记录才采用默认值。
- `init-db.sh` 和 `start.sh` 优先使用显式设置的 `WORKBENCH_PERSISTENT_ROOT`，否则读取本地路径文件，最后使用默认目录。`WORKBENCH_DATABASE_URL` 若显式设置则保留；否则由有效持久目录和固定文件名 `agents.sqlite3` 推导。环境变量覆盖仅作用于当前进程，不重写路径文件。
- 路径必须为绝对路径。脚本应正确处理空格和符号链接；实际数据库路径必须位于有效持久目录内。切换目录不迁移、复制或删除旧数据。

## 三阶段行为

1. `install.sh` 检查工具、安装锁定依赖、构建 Web，并仅在本地配置缺失时复制示例。它记录路径选择，但不创建、迁移或启动数据库。重复运行不得覆盖现有配置或重选数据目录；显式传入不同的 `--data-dir` 时更新选择并提示旧数据不会移动。
2. `init-db.sh` 使用相同的路径解析规则，仅对尚不存在的数据库文件依次运行 migrate、bootstrap、doctor。已有数据库或符号链接一律拒绝；失败不删除或重置已有数据。升级已有数据库仍走维护手册。
3. `start.sh` 使用相同的路径解析规则，先执行 doctor，再启动 API、Worker、Scheduler；`--mcp` 仍为可选。它不自动初始化或迁移数据库，现有进程清理行为保持不变。

## 兼容与验证

已有用户若已设置两个环境变量，行为保持不变。现有 `agent.yaml` 中的 `env://WORKBENCH_DATABASE_URL` 引用不改；脚本在调用 Agent 前注入解析出的值。非默认数据库名继续通过环境变量指定。配置文件、模型密钥和数据目录仍按现有边界管理，不把实际密钥写进仓库。

脚本测试覆盖默认目录、自定义目录、重复安装、环境变量优先级、路径含空格、已有数据库拒绝、有效配置指向目录外数据库时拒绝，以及日常启动不迁移。README 和本地运行手册给出克隆后的三个命令及覆盖目录的示例。
